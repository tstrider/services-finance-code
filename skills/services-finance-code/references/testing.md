# Testing Finance Code

The difference in finance: a green test suite over wrong data is the usual failure. Tie-out tests matter more than unit tests.

## The test that matters most

**Tie to the source system, per period, automatically.** If the pipeline does not check its output against the accounting system's own report for the period, no other test makes up for it.

```python
def test_revenue_ties_to_source_report(period):
    ours = pipeline_revenue_total(period)
    theirs = source_system_income_statement_revenue(period)   # the system's own report, not our query
    assert ours == theirs, f"{period}: ours {ours}, source {theirs}, delta {ours - theirs}"
```

For a one-off analysis, this is the tie-out block in the report. For anything that runs again, it is a test.

## Golden datasets

A fixed set of inputs with expected outputs, agreed with the finance owner.

- **Agreed, not generated by the code.** If the expected values came from running the code, the test only proves the code does what it does.
- **Real shapes, made-up values.** Cover the real mess: late time entries, a mid-scope rate change, a credit memo, a write-down, a partial month start, a second currency, a 53-week year if the firm uses one.
- **Versioned with the logic.** When logic changes on purpose, the golden set changes on purpose, with approval.
- These are acceptance criteria as much as tests.

## Property tests for money

Some rules hold for every input. Test the rule, not a few examples. Needs `hypothesis`.

```python
from decimal import Decimal
from hypothesis import given, strategies as st
from money import allocate, assert_balanced

cents = st.decimals(min_value=Decimal("-1000000"), max_value=Decimal("1000000"),
                    places=2, allow_nan=False, allow_infinity=False)

@given(total=cents, weights=st.lists(st.integers(1, 1000), min_size=1, max_size=50))
def test_allocation_always_adds_back(total, weights):
    assert sum(allocate(total, weights, "USD")) == total
```

Rules worth testing this way: allocations add back, debits equal credits, signs survive a transform, currencies never mix silently, opening plus activity equals closing, and totals are the same whichever order dimensions are grouped.

## Tests for the tie-out itself

Test that the pipeline reports what it drops, not just its output.

```python
def test_no_silent_row_loss(sample):
    result = transform(sample)
    assert result.rows_out == result.rows_in - result.rows_excluded
    assert result.total_out == result.total_in - result.total_excluded

def test_orphan_invoice_is_kept_and_reported(sample_with_unknown_client):
    result = transform(sample_with_unknown_client)
    assert result.unmatched_count == 1       # visible
    assert result.rows_out == result.rows_in # not dropped
```

**A pipeline that silently drops a row must fail a test.** This is the most valuable test class in finance code and it is usually missing.

## Edge cases that really happen

Build fixtures for these. They arrive every quarter.

**Time and billing**
- Time entered after the cut-off for a prior period
- Time entry edited after invoicing
- A person with two roles in one month
- Rate card change in the middle of a scope
- Two rate card versions that overlap, and a gap between versions
- Fixed-fee scope that ends mid-month
- Write-down on part of an invoice
- Hours on a scope with no rate for that role

**Periods and dates**
- Fiscal year not starting in January
- 53-week year or 4-4-5 periods, if the firm uses them
- A transaction on a period boundary in a different time zone
- Leap day
- A backdated entry into a closed period (must be refused)

**Amounts**
- Zero
- Negative revenue (credit memo, refund)
- Amounts smaller than a cent before rounding
- Very large amounts near the column's precision
- JPY (0 decimals) or KWD (3 decimals) next to USD
- The 100 split three ways case
- A zero weight in an allocation
- A 100% discount

**Data**
- Duplicate invoice numbers with different punctuation (`INV-001`, `INV001`, `inv 1`)
- Client with no invoices
- Invoice with no matching client
- Blank where a rate is expected
- A reversal of a reversal

**Process**
- A retried payment or invoice batch (must not duplicate)
- A job stopped halfway through an allocation
- Period locked while a job runs
- Two people editing the same record

## What not to test

- Python's Decimal arithmetic
- The accounting system's own calculations
- That a sum sums
- Snapshot tests of large outputs nobody reads. Approving a regenerated snapshot without looking turns a bug into an expected value.

## Testing against real systems

- **Never test against production.** Use a sandbox or test company. QuickBooks, Xero, and most ERPs offer one.
- Record API responses once and replay them in tests. Live tests are slow and flaky.
- Test the failures on purpose: rate limit, timeout, partial page, period locked, bad response, login expired midway.
- Test resuming from a checkpoint, not just clean runs.
- Test data is made up. Never copy real records into fixtures.

## Parallel run

Anything that replaces an existing process needs more than a test suite.

Run old and new side by side for at least one full cycle. **Reconcile every difference to zero or explain each one.** "Just rounding" usually is not. Never cut over on a green suite alone.

## Review checklist for tests

- [ ] Ties to an independent source, as a test
- [ ] Row counts and totals checked across every join and filter
- [ ] Decimal throughout
- [ ] Allocations checked to add back
- [ ] Rate lookups tested across a rate change
- [ ] Late time and cut-off tested
- [ ] Retries tested to never duplicate
- [ ] Golden scenarios agreed with the finance owner
- [ ] No sensitive data in fixtures, logs, or test output
